### 5. デザインシステム（case-design-system）の適用方針

本人の意向として「デザインシステムを採用してサイトを構築したい」。ただし論点が3つある。

1. **技術スタックが違う** — このサイトは Material-UI、case-design-system は
   React Aria + vanilla-extract。適用するには MUI を剥がす大工事になる
2. **用途が違う** — case-design-system は「業務・管理画面向け」と明記されている。
   ポートフォリオサイトは業務画面ではない。用途の違うものを無理に当てると両方歪む
3. **まだ実装が無い** — コミット1つ、docs（principles / decisions / status）のみ

考えられる進め方:

- **A. サイト全体を作り直す** — 用途の違いを無視することになる。大工事
- **B. デザインシステムのショーケースを1ページ作る** — サイト本体は MUI のまま、
  「このデザインシステムで作った業務画面の例」を見せる。用途を混ぜずに実物を示せる。
  case-design-system 側の「具体的な場面から原則を逆算する」方針とも合う
- **C. 先に case-design-system を実装まで進める** — サイトは触らない

未決。なお case-design-system 側には `/design-walkthrough` スキルがあり、
専用の進め方が用意されている。

### 6. 中身とサイトの層分け（2026-09-12、Issue #7）

本人の意向: **中身のデータも画像も、サイトとは別に管理したい。情報設計の層を分けたい。**

いまは層が分かれていない。`Divide and Conquer` の基準は「分けること」ではなく
「独立して解けること」で、その基準では両方向とも落第している。

- 中身を変えるとサイトの再ビルド・再デプロイが要る
- 写真を差し替えるのも同じ（毎回 124MB を転送している）
- 削るルール（`profileTransform.mjs`）がサイト側にあり、見せ方の担当が
  公開してよい範囲の判断まで持っている

目指す形は3層。原本（非公開・Markdown）→ 配信用コンテンツ（公開可・R2 など）→
サイト（見せ方だけ）。**写真の問題とプロフィールの問題は同じ問題**であり、別々に解かない。

**分けただけでは悪化する。** サイトが中身の形を暗黙に知っているままなら、結合が
「同じリポジトリ」から「どこにも書かれていない約束」へ移るだけで、誰も検査しなくなる分
悪くなる。このリポジトリ群では同じ形の失敗が既に3回起きている（AGENTS.md の写し、
Secret のズレ、sample.json の二役）。**境界を作るたびに検査を置くこと。**

詳細と決めるべき項目は Issue #7。

### 7. プロフィールの正本が届く経路（2026-09-12、Issue #6）

**暫定で案 A（`PROFILE_JSON_B64` を Secrets に登録）を採る判断をした。**

案 B（公開用 JSON をこのリポジトリにコミットする）は、ズレが git の差分で見える利点が
あるが、**中身をサイトのリポジトリに同居させる**ことと引き換えであり、上記の層分け方針と
真逆だったため採らない。

A のズレ問題（Secret は書けるが読めないため、正本が更新されてもサイトは古いまま、
かつ誰も気づけない）は解消しない。暫定であることを前提に受け入れる。恒久策は Issue #7。

**2026-09-12 に完了。公開サイトは実データを表示している。**

`PROFILE_JSON_B64` を登録し、`PROFILE_ALLOW_SAMPLE` を削除した。
サンプルへのフォールバックが無く `profile.source.json` も CI に存在しないため、
**ビルドが通ること自体が Secret を正しく読めたことの証明**になっている。

値は正本側の `公開用/profile.source.json` から生成したもので、正本の
「公開時の表示」列だけで作られている。A の弱点（Secret は書けるが読めない）は
残るが、守るべき値が入っていないためズレても漏れない。

途中、最初に貼った base64 が壊れてビルドが `SyntaxError` で落ちた。
`npm run` のバナーが混入し、`Buffer.from(x, 'base64')` がそれを黙って読み飛ばして
中身がずれていた。`scripts/generate-profile.mjs` を直し、復号結果が JSON でなければ
停止するようにした。生の JSON も受け付ける（Secrets は複数行を保持できる）。

残件: `biography` は AI の下書きのまま、`strengths_finder.top_5` / `skills` /
`social_links` は空。埋める材料として本人の Wantedly 公開プロフィールが候補
（クラウド実行環境からは egress 制限で取得できないため、本人からの提供が要る）。

### 8. 実データを入れるときの前提

`PROFILE_JSON_B64` を設定する前に、正本側で `*Display` 系の値を全て埋めておくこと。
書き忘れがあると**実名にフォールバックせずビルドが停止する**（安全側だが、デプロイは失敗する）。
