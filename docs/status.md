## 2026-09-12 に起きたこと（Issue #3 / デザインシステムの流し込み）

サイトの配色と文字サイズを、デザインシステムのトークンから作るようにした。
**`src/theme.ts` から16進のリテラルが1つも無くなった。**

1. **色を式から生成するようにした。** `src/tokens/` に、明度・彩度・色相と、
   それを組む式を写した（値の一覧ではない。値を貼ると、向こうで明度を1ポイント
   動かしたときにこちらの差分が「意味のない16進の羅列」になって読めなくなる）
2. **OKLCH → sRGB の変換を自前で持った**（`src/tokens/oklch.ts`）。
   MUI は渡された色を自分で明暗に振ったり透明度を掛けたりするが、その実装が
   受け付けるのは `#nnn` / `rgb()` / `hsl()` / `color()` だけで、`oklch()` も `var()` も
   例外になる。**「CSS 変数をそのまま MUI に渡す」は成立しない**ので、変換をここに置いた。
   色域外の指定は明度と色相を保ったまま彩度だけを落として収める（＝コントラストを動かさない）
3. **文字サイズを流体（`clamp`）にした。** 320px〜1440px の間で連続的に変わる。
   `clamp` の中間項に `rem` が入っているので、画面幅だけでなく
   **ブラウザの文字サイズ設定にも追従する**
4. **配色がOSの設定に従うようになった。** 3状態（システムに従う／ライト／ダーク）。
   既定は「システムに従う」で、これは localStorage に**保存しない**ことで表現している
   （値として保存すると、明示的に選んだ人と何もしていない人の区別がつかなくなる）。
   以前は初回描画時に一度 `matchMedia` を読むだけで、OS 側を切り替えても追従しなかった
5. **生の数値を消した。** `fontSize: '1.1rem'` や `fontSize: { xs: 14, sm: 16 }` を
   トークン参照に置き換えた。残っているのは SVG の属性と、アバターの比率計算だけ

### ついでに直ったもの

- **トップページの見出しが独自指定でスケールを外れていた**（`2.5rem` / `3.5rem`）。
  外して h2（33〜45px の流体）に任せた
- **ブラウザの文字サイズを 200% にすると About が横に溢れていた**（390px 幅で 82px）。
  原因は Chip が1行固定だったことと、grid の列が `1fr`（= `min-width: auto`）だったこと。
  Chip を折り返せるようにし、列を `minmax(0, 1fr)` にした

### 確かめたこと（ヘッドレス Chrome、実測）

| 見たもの | 結果 |
|---|---|
| ライト／ダーク × 390px・1440px × 5ページ | コンソールエラーなし、横スクロールなし |
| 本文のコントラスト比 | ライト 10.31、ダーク 12.48（どちらも最小値） |
| 文字サイズ 200%（root 32px）での横溢れ | 0px（4画面） |
| 3状態の切り替え | システム→ライト→ダーク→システム、保存も期待どおり |

### デザインシステム側に返した修正

実測の過程で、**ライトの `textMuted` が AA を割っていた**のが見つかった
（`bg` の上で 4.41:1）。明度を役割に予約すればコントラストは計算で保証される、という
前提が、**その計算を回していなかった**ために破れていた。向こうで 55% → 54% に直してある。

## 2026-09-13 に起きたこと（Issue #7 / 層分けの本体）

### 1. 原本を配信物から外した（dist 124MB → 708KB）

`public/` は Vite が `dist/` へ丸ごと写す場所で、写真の原本 120MB がそこにあった。
**誰も参照していないのに、デプロイのたびにアップロードされていた。**
原本は「変換の入力」であって「配るもの」ではないので `originals/` へ移した。

プロフィール画像も同じで、2784x1856 の 3.6MB をそのまま配っていた。
丸いアバターの実寸は 100〜150px。320/640/1600 の3段を作り、サイトは層2 から取りに行く
（丸には 320px の webp が 15KB、拡大表示のときだけ 1600px を取る）。
**これで `public/` から中身が全部消えた。**

### 2. 削る処理をこのリポジトリから消した

**このリポジトリは削らない。届いたものを検査するだけになった。**

`profileTransform.mjs`（何を隠すかの設定と変換）はもう誰も呼んでいなかった。
サイトは実行時に層2 から取りに行っており、層2 に届く時点で既に表示用の値になっている。
にもかかわらず、`PROFILE_JSON_B64` が無いとビルドが落ちる状態だけが残っていた。

消したもの: `PROFILE_JSON_B64` / `generate-profile.mjs` / `print-profile-b64.mjs` /
`profileTransform.mjs` / `profile.sample.json` / `verify:redaction` /
`*Display` フィールドの必須規則。

### 3. 境界に「入っていてはいけないもの」の検査を足した

**これが Issue #7 の成否を決める部分。** それまでのスキーマは `required` と `type` しか
書いておらず、「あるべき形」だけを定義していた。それは「書かれていないものは
何でも通る」という意味になる。公開しないと決めた項目（`gender` / `nationality` /
`all_ranking`）を原本側で足しても、配信経路は黙って通していた。

- `x-forbiddenKeys` を契約に足し、入れ子の**全階層**で探して見つかれば止める
- `basicInfo.birthday` に `pattern: ^[0-9]{4}$`。「年だけ」はキーの名前では表せない
- **検査器そのものを検査するケース**（`boundary-cases.mjs`）を両側に置いた。
  壊れた検査器は「全部通った」と言うので、データの検査より先にこちらを見ないと意味がない
- 契約から条項が消されていないかを見る `checkContract` を送り出す側に置いた。
  実装の自己確認だけだと、`x-forbiddenKeys` を消されても何も言わずに通る

スキーマの版を 1.1.0 に上げた。形は変わっていないが制約が変わっている。

### 4. 開発サーバでも `/api/*` が応えるようになった

`dev-data/` に置けばそれを返し、無ければ本番の Worker へ取りに行く。
契約の写しを手元に常備しない形にしてある（写しを置いた瞬間、古くなる番が始まる）。

### Issue #7 の完了条件に対して

| 条件 | 状態 |
|---|---|
| 中身を変えてもサイトを再デプロイせずに済む | ✅ プロフィール・写真とも層2 から実行時取得 |
| サイトのリポジトリから中身のデータが消えている | ⚠️ 配信物からは消えた（`dist` 708KB）。写真の原本は `originals/` に残っている（下記） |
| 層間のスキーマ検査があり、破ると止まる | ✅ 両側にある。検査器の自己確認つき |
| `docs/status.md` に層の図と置き場所 | ✅ `docs/profile-privacy.md` に図がある |

### 残っている穴（正直に書く）

- **写真の原本 120MB はまだリポジトリにある。** `dist` には入らなくなったが、
  クローンすると付いてくる。R2 へ移すには手元から上げる手段が要る（API トークンは
  GitHub Secrets にしかない）。履歴からの削除は破壊的なので本人の判断が要る
- **検査器の写しが片側だけ書き換えられても検出できない。** 両側に同じ
  `boundary-cases.mjs` を置いてあるが、それ自体が写しなので同じ問題を抱えている

### 5. デザインシステムの適用方針 → **トークンだけ流し込む形で決着**（2026-09-12、Issue #3）

当初の論点は「MUI を剥がすか否か」だった。剥がさない。**色と型のトークンだけを写して、
MUI のテーマへ流し込む。** 部品（React Aria + vanilla-extract の実装）は持ってこない。

理由: 揃えたいのは**見え方**であって、部品の実装ではない。
部品まで持ってくると MUI を剥がす大工事になり、その工事が終わるまで
サイトの見た目は1ミリも変わらない。トークンだけなら1日で変わる。

**依存（npm パッケージ）にはしていない。** デザインシステムはまだ毎週かたちが変わる段階で、
依存を先に張ると片方を触るたびに両方を動かす羽目になる。いまは**写し**で受けて、
ずれたら手で揃える。揃える作業が面倒になった時点が、依存に切り替える合図。

残っている論点:

- **写しがずれる。** `src/tokens/index.ts` の冒頭に、写した日付と原本のコミットを書いてある。
  これは検査ではなく申告なので、放っておけば古くなる（境界を作るたびに検査を置く、が
  まだ守れていない1箇所）
- **色相を実行時に変えられなくなっている。** 原本は `--ds-hue` という CSS 変数で
  色相を差し替えられるが、こちらはビルド時に 265 で固定している。
  MUI が受け取れる色の書式に `oklch()` も `var()` も含まれないため
  （詳しくは `src/tokens/oklch.ts` の冒頭）
- **ショーケースを1ページ作る案は消していない。** トークンを流し込むことと、
  「このデザインシステムで作った業務画面の例」を見せることは別の話

### 6. 中身とサイトの層分け → **ほぼ決着**（2026-09-13、Issue #7）

> 実装と残件は上の「2026-09-13 に起きたこと」を参照。
> 残っているのは（a）写真の原本 120MB がまだリポジトリにあること、
> （b）検査器の写しが片側だけ書き換えられても検出できないこと の2つ。
> 以下は当初の問題設定（記録として残す）。

本人の意向: **中身のデータも画像も、サイトとは別に管理したい。情報設計の層を分けたい。**

いまは層が分かれていない。`Divide and Conquer` の基準は「分けること」ではなく
「独立して解けること」で、その基準では両方向とも落第している。

- 中身を変えるとサイトの再ビルド・再デプロイが要る
- 写真を差し替えるのも同じ（毎回 124MB を転送している）
- 削るルール（`profileTransform.mjs`）がサイト側にあり、見せ方の担当が
  公開してよい範囲の判断まで持っている

目指す形は3層。原本（非公開・Markdown）→ 配信用コンテンツ（公開可・R2 など）→
サイト（見せ方だけ）。**写真の問題とプロフィールの問題は同じ問題**であり、別々に解かない。

**分けただけでは悪化する。** サイトが中身の形を暗黙に知っているままなら、結合が
「同じリポジトリ」から「どこにも書かれていない約束」へ移るだけで、誰も検査しなくなる分
悪くなる。このリポジトリ群では同じ形の失敗が既に3回起きている（AGENTS.md の写し、
Secret のズレ、sample.json の二役）。**境界を作るたびに検査を置くこと。**

詳細と決めるべき項目は Issue #7。

### 7. プロフィールの正本が届く経路 → **暫定策ごと不要になった**（2026-09-13、Issue #6）

> `PROFILE_JSON_B64` は廃止した。ビルドに中身の入力が要らなくなったため
> （実行時に層2 から取りに行く）。A の弱点だった「Secret は書けるが読めないので
> ズレても誰も気づけない」は、**ズレる対象が無くなったことで消えた**。
> 以下は当初の判断（記録として残す）。

**暫定で案 A（`PROFILE_JSON_B64` を Secrets に登録）を採る判断をした。**

案 B（公開用 JSON をこのリポジトリにコミットする）は、ズレが git の差分で見える利点が
あるが、**中身をサイトのリポジトリに同居させる**ことと引き換えであり、上記の層分け方針と
真逆だったため採らない。

A のズレ問題（Secret は書けるが読めないため、正本が更新されてもサイトは古いまま、
かつ誰も気づけない）は解消しない。暫定であることを前提に受け入れる。恒久策は Issue #7。

**2026-09-12 に完了。公開サイトは実データを表示している。**

`PROFILE_JSON_B64` を登録し、`PROFILE_ALLOW_SAMPLE` を削除した。
サンプルへのフォールバックが無く `profile.source.json` も CI に存在しないため、
**ビルドが通ること自体が Secret を正しく読めたことの証明**になっている。

値は正本側の `公開用/profile.source.json` から生成したもので、正本の
「公開時の表示」列だけで作られている。A の弱点（Secret は書けるが読めない）は
残るが、守るべき値が入っていないためズレても漏れない。

途中、最初に貼った base64 が壊れてビルドが `SyntaxError` で落ちた。
`npm run` のバナーが混入し、`Buffer.from(x, 'base64')` がそれを黙って読み飛ばして
中身がずれていた。`scripts/generate-profile.mjs` を直し、復号結果が JSON でなければ
停止するようにした。生の JSON も受け付ける（Secrets は複数行を保持できる）。

残件: `biography` は AI の下書きのまま、`strengths_finder.top_5` / `skills` /
`social_links` は空。埋める材料として本人の Wantedly 公開プロフィールが候補
（クラウド実行環境からは egress 制限で取得できないため、本人からの提供が要る）。

### 8. 実データを入れるときの前提

`PROFILE_JSON_B64` を設定する前に、正本側で `*Display` 系の値を全て埋めておくこと。
書き忘れがあると**実名にフォールバックせずビルドが停止する**（安全側だが、デプロイは失敗する）。
