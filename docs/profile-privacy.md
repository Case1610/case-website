# プロフィールの非公開制御について

**プロフィールを触る前にここを読むこと。**

## 一行でいうと

**このリポジトリは削らない。届いたものを検査するだけ。**

削るのは正本の側（別の非公開リポジトリ）で、こちらは「届いてはいけないものが
届いていないか」を見る。送る側が削り、受ける側が検査する。

## 層

```
層1  原本                非公開リポジトリ。人間が書く Markdown
      │  生成・抽象化・表示の判断はここで終わらせる
      │  送り出す前に検査する（通らなければ上げない）
      ▼
層2  配信用コンテンツ     R2（バケット case-content）
      │  profile.json / schema.json / media/*
      │  公開されている。守るべき値は入っていない
      ▼
層3  このサイト           見せ方だけ。中身を持たない
         実行時に /api/* で取りに行き、受け取った側でも検査する
```

`/api/*` は `worker/index.ts` が R2 から返している。同一オリジンなので、
ブラウザから見ると自分のサイトのファイルを読んでいるのと変わらない。

## このリポジトリにプロフィールのデータは無い

| もの | どこにあるか |
|---|---|
| 原本 | 別の非公開リポジトリ（Markdown） |
| 配信用の JSON | R2。`/api/profile.json` |
| 契約（スキーマ） | R2。`/api/schema.json` |
| 契約の TypeScript 版（写し） | `src/types/profile.d.ts` |
| 受け取り側の検査器 | `src/data/profileSchema.mjs` |
| 検査器を検査するケース | `scripts/boundary-cases.mjs` |

**バンドルにプロフィールのデータは1バイトも載らない。** 載るのは取得先の URL だけ。

以前はビルド時に実データを読み込んで JSON を作り、それを `import` していた。
Vite は `import` された JSON を**静的にバンドルへ埋め込む**ため、画面に出していない
項目まで全部が訪問者に届いていた。いまはその経路そのものが無い。

`npm run verify:boundary` がこの性質を守っている。`src/pages/` にプロフィールの
JSON が置かれたり、どこかが `.json` を `import` し始めたら、そこで止まる。

## 契約は2種類のことを言う

`schema.json` には向きの違う2つの規定がある。**片方だけでは足りない。**

| 書き方 | 言っていること |
|---|---|
| `required` / `type` / `pattern` | **入っているべきものが入っているか** |
| `x-forbiddenKeys` | **入っていてはいけないものが入っていないか** |

後者が無いと、「書かれていないものは何でも通る」という意味になる。
原本の側で新しい項目を足したときに、公開してよいかの判断を誰も通さないまま
配信経路に乗ってしまう。

現在の `x-forbiddenKeys`:
`gender` / `nationality` / `all_ranking` / `address` / `phone` / `phoneNumber` / `postal_code`

入れ子の**全階層**で探す。`career[0].address` のように深いところに紛れても見つかる。

`pattern` は形の制約で、いまは `basicInfo.birthday` に `^[0-9]{4}$`（年だけ）が
かかっている。「年だけであること」はキーの名前では表せず、完全な生年月日が
入ってきても型としては文字列で通ってしまうため。

## 検査は両側にある

同じ `schema.json` を、送り出す側（正本リポジトリの CI）と受け取る側（ブラウザ）の
両方が使う。片側だけの検査は、もう片側が黙って形を変えられることを意味する。

検査器の実装（`validateAgainstSchema`）も**両側に1つずつある**。
両方が同じように振る舞わなければ「検査が両側にある」は嘘になるので、
検査器そのものを検査するケース（`scripts/boundary-cases.mjs`）も両側に同じものを置き、
両方の CI で走らせている。

### 片側だけの書き換えは、指紋で検出する（2026-09-13）

写しが2つある以上、**片側だけ直されたら気づけない**。そこで、
ケースを走らせた結果を1本のハッシュに畳み、**契約（`schema.json`）の
`x-checkerFingerprint` に置いた。**

- 契約は層2 にひとつしか無い
- 片側を直して指紋を更新すると、**もう片側が落ちる**
- 実装とケースの**両方**が材料なので、ケースの写しがずれても検出される

CI は `dev-data/schema.json` があればそれを、無ければ公開されている
`/api/schema.json` を読む。**どちらも駄目なら止まる。**
契約を確かめずに配るくらいなら、配らないほうがいい。

> **指紋の限界**: ケースが触る範囲しか見ない。どのケースも通らない枝で
> 両側が食い違っていても、指紋は同じままになる。実際、禁止キーの探索を
> 浅い階層で打ち切る改竄は、最初どのケースにも引っかからなかった
> （「4階層下の禁止キーも見つかる」を足して塞いだ）。
> **検査の範囲を広げる唯一の方法は、ケースを足すこと。**

## 取得に失敗したときは、失敗したと言う

`ProfileProvider` は失敗しても既定値で埋めない。`ProfileGate` が
「読み込めませんでした」と理由を出す。

空欄は「まだ無い」と読めるが、それらしい値で埋めた画面は「これが事実だ」と読まれる。
2025年から1年以上、架空の人物（サンプルデータ）が公開サイトに出ていたのは、
サンプルが「検証の土台」と「本番のフォールバック」を兼ねていたためだった。
落ちるのは、気づけるからである。

## 型にも置かない

`src/types/profile.d.ts` には `gender` も `nationality` も無い。

型に残しておくと「いつか来るかもしれない」という顔をするが、`x-forbiddenKeys` は
それが来たら止めると言っている。片方が「来るかも」、もう片方が「来たら止める」では、
読む人が判断できない。

## 開発するとき

```bash
npm run dev
```

`/api/*` は開発サーバが肩代わりする（`vite.config.ts` の `layer2Dev`）。

1. `dev-data/` に同じ名前のファイルがあればそれを返す（手元で中身を変えて試せる）
2. 無ければ本番の Worker へ取りに行く

契約（`schema.json`）の写しを手元に常備しない形にしてある。写しを置いた瞬間、
それが古くなる番が始まるため。

## 検証

```bash
npm run verify:boundary
```

- 受け取り側の検査器が、契約の書き方（`required` / `type` / `pattern` /
  `x-forbiddenKeys` / 版の一致）を正しく解釈するか（9ケース）
- その振る舞いが、送り出す側と食い違っていないか（契約の指紋と突き合わせる）
- プロフィールがバンドルへ焼き込まれる経路に戻っていないか

CI でもビルド前に実行され、失敗するとデプロイまで進まない。

## 廃止したもの（2026-09-13）

| もの | なぜ消したか |
|---|---|
| `PROFILE_JSON_B64`（Secret） | ビルドに中身の入力が要らなくなった |
| `scripts/generate-profile.mjs` | 同上 |
| `src/utils/profileTransform.mjs` | 削るのは正本の側。こちらに置くと同じ規則が2箇所になる |
| `src/pages/profile.sample.json` | 「検証の土台」と「本番のフォールバック」を兼ねていた |
| `npm run verify:redaction` | `verify:boundary` に置き換え |
| `*Display` フィールドの必須規則 | 削る処理ごと無くなった。層2 に届く時点で既に表示用の値 |

Secret はもう使っていないが、GitHub に残っていても害は無い（中身は原本の
「公開時の表示」列だけで作られており、守るべき値が入っていない）。消すのは任意。
